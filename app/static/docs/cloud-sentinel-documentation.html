O que é o Cloud Sentinel

O Cloud Sentinel é uma plataforma open source de assessments AWS. Ela coleta dados reais da conta AWS do cliente, processa-os com inteligência artificial (Claude da Anthropic) e entrega relatórios detalhados de custo (FinOps) e segurança — tudo em português, com foco em ação.

20+
Tipos de dado AWS coletados
50+
Verificações de segurança
5
Dimensões de maturidade FinOps
400+
Checks via Prowler (opcional)
Proposta de valor: em vez de dashboards genéricos, o Cloud Sentinel entrega diagnóstico contextualizado por conta — incluindo quick wins priorizados por ROI, score de maturidade FinOps e score de segurança com detalhamento de cada finding.

Para quem é cada parte

PerfilO que acessaURL
Admin / Consultor Painel admin completo — cria clientes, dispara análises, edita recomendações, gera PDFs /admin
Cliente Portal read-only com os resultados visíveis da análise mais recente — scores, quick wins, projetos /portal/{token}

Modelo de Acesso à Conta do Cliente

O Cloud Sentinel nunca armazena credenciais permanentes dos clientes. O acesso é feito via STS AssumeRole:

Pod no EKS
Usa IRSA para assumir cloud-sentinel-role na conta sandbox
→
2
STS AssumeRole
Assume FinOpsAnalyzerRole na conta do cliente via cross-account
→
3
Coleta de Dados
boto3 coleta dados de 20+ serviços com credenciais temporárias (1h)
→
4
Análise IA
Dados enviados ao Claude para análise FinOps + Segurança
→
5
Relatório
Resultados salvos no banco, visíveis no painel e portal
Pré-requisito no cliente: a role FinOpsAnalyzerRole (ou nome customizado) deve ter trust policy autorizando a conta AWS que hospeda o Sentinela a fazer AssumeRole.
03

Como Funciona uma Análise

Uma análise completa passa por 6 etapas principais, exibidas em tempo real com progress bar no painel admin. Cada etapa tem nome, percentual e indicador visual.

#EtapaO que aconteceDuração Típica
1 Conexão AWS STS AssumeRole valida o acesso à conta. Falha aqui = role incorreta ou sem trust policy ~2s
2 Coleta de Dados 20+ coletores AWS rodam em paralelo (6 workers globais + 4 regionais). Cobre custos, segurança, utilização, versões 30–90s
3 Análise FinOps (IA) Claude analisa custos, gera maturity model, quick wins, projetos e resumo executivo de FinOps 30–120s
4 Análise de Segurança (IA) Claude analisa findings de IAM, S3, rede, criptografia, compliance, versões. Gera score e recomendações 30–120s
5 Análise Combinada (IA) Cruzamento FinOps × Segurança — identifica riscos que afetam custo E segurança ao mesmo tempo 20–60s
6 Finalização Dados persistidos no banco. Status: completed ou partial se alguma etapa IA falhou ~2s
Status "Parcial": ocorre quando as etapas AWS funcionam mas alguma chamada de IA falha (ex.: sem API key, timeout). Os dados brutos ainda ficam salvos — é possível executar "Somente IA" a partir do detalhe do cliente para completar sem reprocessar a AWS.

Paralelização da Coleta

Para reduzir o tempo de coleta em contas com múltiplas regiões, os coletores são divididos em dois grupos paralelos:

Fase 1 — Coletores Globais (6 workers simultâneos)

Cost Explorer, Savings Plans, Cost by Tag, IAM, S3, Trusted Advisor, Cost Anomalies

Fase 2 — Coletores Regionais (4 workers por região)

EC2 + CloudWatch, RDS, Lambda, ECS/EKS, NAT Gateway, Security Groups, GuardDuty, Config, CloudTrail, Encryption, CloudFront

Score de Segurança

Cálculo do Score

O score vai de 0 a 100 e usa modelo de dedução por severidade. Começa em 100 e cada finding encontrado desconta pontos:

# Fórmula de cálculo
score = 100
score -= findings_critical × 20  # cada critical = -20 pts
score -= findings_high × 10  # cada high = -10 pts
score -= findings_medium × 5  # cada medium = -5 pts
score = max(0, min(100, score)) # clamp 0–100
ScoreRótuloInterpretação
85 – 100Excelente0 critical, 0–1 high, poucos medium. Conta bem gerenciada.
70 – 84Bom0 critical, até 3 high, alguns medium. Pontos de atenção tratáveis.
50 – 69Regular0–1 critical ou muitos high/medium. Risco real mas gerenciável.
30 – 49Ruim1–2 critical ou alto volume high. Exposição significativa.
0 – 29Crítico3+ critical. Conta com risco severo — ação imediata necessária.

FinOps Score

O FinOps Score é um número único de 0 a 100 que resume a saúde financeira e a maturidade em gestão de nuvem do cliente. Ele é o único indicador de performance FinOps exibido no dashboard — consolidando o que antes eram dois scores separados (Cost Health Score e Maturity Model) em um único número acionável.

Fórmula e Pesos

O FinOps Score é uma média ponderada de dois componentes independentes:

# Componentes
cost_health_score = número inteiro gerado pelo Claude AI (0–100)
maturity_pct = overall_maturity_score × 10  # converte escala 0–10 → 0–100

# Score final
finops_score = round( cost_health_score × 0.6 + maturity_pct × 0.4 )

# Custo tem peso 60%, Maturidade tem peso 40%
# Resultado: inteiro entre 0 e 100

O peso maior no componente de custo (60%) reflete que a saúde financeira imediata é mais urgente que a maturidade de processos. Um cliente pode ter bons processos mas custo fora de controle — nesse caso o score cai mesmo com maturidade alta.

Custo controlado, processos iniciais 75 pts 30 pts (score 3/10) 57  Regular
Desperdício alto, sem processos 30 pts 10 pts (score 1/10) 22  Fraco

Componente 1 — Cost Health Score (peso 60%)

O Cost Health Score é gerado pelo Claude AI após analisar os dados brutos coletados da conta AWS. Não é uma fórmula fixa — é um juízo contextualizado sobre a saúde financeira atual: não apenas "quanto você gasta" mas "quanto você poderia economizar, qual é a tendência e você está pagando o preço certo".

O Claude considera os seguintes sinais para determinar o score:

💸 Savings Potential

Estimativa de quanto do custo atual poderia ser economizado com rightsizing, eliminação de desperdício e commitments. Potencial >30% → score baixo. <5% → score alto.

📈 Tendência de Custo

Variação mês a mês. Crescimento >15% penaliza o score. Queda >5% melhora. O Claude considera se o crescimento é justificado por crescimento do negócio ou desperdício.

📋 RI/SP Coverage

Percentual do gasto coberto por Savings Plans ou Reserved Instances. Abaixo de 30% impacta negativamente — workloads previsíveis pagando preço On-Demand.

🔖 Versões Deprecadas / EOL

RDS em Extended Support e Lambdas com runtimes deprecated geram custo extra mensurável. Cada recurso nessa situação é cobrado a mais sem ganho de valor.

🗑️ Recursos Ociosos

EBS desanexados, EIPs não associados, snapshots antigos, instâncias paradas e LBs sem targets — cada um é desperdício direto identificado nos dados coletados.

🚨 Anomalias de Custo

Picos detectados pelo Cost Anomaly Detection nos últimos 30 dias. Anomalias não investigadas indicam falta de controle e impactam negativamente o score.

Componente 2 — Maturidade FinOps (peso 40%)

O componente de maturidade avalia em que estágio de evolução está a gestão de custos do cliente — independente do valor absoluto do gasto. Um cliente pode gastar pouco mas sem nenhum processo (Crawl), ou gastar muito com processos excelentes (Run).

O Claude avalia 5 dimensões independentes, cada uma com score 0 a 10. A média das 5 dimensões forma o overall_score (0–10), multiplicado por 10 para obter a contribuição percentual:

# As 5 dimensões, cada uma de 0 a 10
d1 = tagging_score
d2 = rightsizing_score
d3 = commitment_coverage_score
d4 = waste_elimination_score
d5 = governance_score

overall_score = (d1 + d2 + d3 + d4 + d5) / 5  # média, resultado 0–10
maturity_pct = overall_score × 10             # converte para 0–100

# Ex: scores [7, 4, 2, 8, 3] → overall = 4.8 → maturity_pct = 48

Cada dimensão recebe um nível qualitativo com base no score:

🐛 Crawl

Score da dimensão: 0 – 3
  • Processos manuais ou inexistentes
  • Pouca ou nenhuma visibilidade
  • Nenhuma automação
  • Remediação reativa

🚶 Walk

Score da dimensão: 4 – 6
  • Processos documentados e repetíveis
  • Visibilidade parcial
  • Algumas automações implantadas
  • Revisões periódicas acontecem

🏃 Run

Score da dimensão: 7 – 10
  • Processos automatizados e otimizados
  • Visibilidade total em tempo real
  • Práticas de engenharia de custos
  • Remediação proativa e preventiva

As 5 Dimensões Detalhadas

🏷️
Tagging
Sinal: tags ativas no Cost Explorer
Avalia a cobertura de tags de alocação de custo na conta. O Cloud Sentinel verifica quais chaves de tag de negócio estão ativas no Cost Explorer — tipicamente Environment, Project e Team.

Crawl (0–3): sem tags ou tagging inconsistente. Impossível alocar custo por projeto ou equipe.
Walk (4–6): 1–2 chaves ativas, cobertura parcial dos recursos.
Run (7–10): 3+ chaves de tag ativas no Cost Explorer, cobertura >70% em recursos EC2, RDS, Lambda e ECS.
⚖️
Rightsizing
Sinal: CPU avg/max via CloudWatch (14 dias)
Avalia se os recursos estão dimensionados corretamente. Uma instância EC2 é considerada superprovisionada quando CPU médio <10% E CPU máximo <25% nos últimos 14 dias. RDS segue critério similar.

Crawl (0–3): >40% das instâncias com utilização muito baixa.
Walk (4–6): 20–40% superprovisionadas, rightsizing em andamento.
Run (7–10): <20% das instâncias superprovisionadas. Compute Optimizer em uso.
💳
Commitment Coverage
Sinal: Savings Plans coverage % via Cost Explorer
Avalia o uso de Savings Plans e Reserved Instances para reduzir custo de workloads previsíveis. O Cloud Sentinel coleta cobertura e utilização diretamente do Cost Explorer via API de Savings Plans.

Crawl (0–3): 0–10% de cobertura. Pagando On-Demand para toda a carga.
Walk (4–6): 10–60% de cobertura com SPs ou RIs.
Run (7–10): >60% de cobertura e >70% de utilização dos compromissos adquiridos.
🗑️
Waste Elimination
Sinal: inventário de recursos ociosos identificados
Avalia a presença de recursos pagos que não geram valor. O Cloud Sentinel identifica: volumes EBS desanexados, EIPs não associados, snapshots antigos (>90 dias), instâncias paradas e Load Balancers sem targets saudáveis.

Crawl (0–3): custo de recursos ociosos >$100/mês ou vários itens acumulados.
Walk (4–6): alguns recursos identificados, remoção em andamento.
Run (7–10): <$20/mês em ociosos. Lifecycle policies e processo de revisão mensal ativos.
🏛️
Governance
Sinal: anomalias, Config, Trusted Advisor
Avalia a maturidade dos processos de governança — alertas, automações e visibilidade proativa. Considera: anomalias de custo nos últimos 30 dias, findings do Trusted Advisor e conformidade de regras do AWS Config.

Crawl (0–3): sem Cost Anomaly Detection ativo, múltiplas anomalias não tratadas, Config desabilitado.
Walk (4–6): anomalias configuradas, alguns findings abertos, Trusted Advisor em uso básico.
Run (7–10): <2 anomalias/mês, todas investigadas, todas as regras Config em compliance.

O Bloco "O que está impactando seu FinOps Score"

Logo abaixo do FinOps Score no dashboard, o Cloud Sentinel exibe automaticamente uma lista priorizada dos principais fatores que estão impedindo o score de chegar a 100. O objetivo é deixar explícito o que precisa ser resolvido — sem que o analista precise "caçar" o problema em páginas diferentes.

O bloco agrega itens de diferentes origens em ordem de impacto:

LabelOrigemO que significa
ANOMALIA Cost Anomaly Detection Pico de custo detectado nos últimos 30 dias — mostra serviço afetado e $ extra/mês
EOL Version Analysis Recurso (RDS, EKS, Lambda) em Extended Support ou deprecated com custo extra identificado
CRAWL Dimensão de maturidade com score 0–3 Dimensão sem práticas básicas — arrasta o componente de maturidade para baixo
WALK Dimensão de maturidade com score 4–6 Dimensão com práticas parciais — tem espaço relevante para evoluir
CRÍTICO / ALTO Service Breakdown (análise por serviço) Serviço com severidade alta e ação recomendada — mostra economia estimada em $/mês
Cada item do bloco de impacto leva o analista diretamente à ação: qual serviço, qual o problema específico, qual a ação recomendada e qual o saving potencial. Resolver os itens no topo da lista tem o maior impacto no score.

Como Atingir FinOps Score 100

Score 100 = Cost Health Score 100 + Maturidade 100. Para isso: zero desperdício, custo estável ou caindo, 100% de cobertura com SPs/RIs, todas as 5 dimensões de maturidade em nível Run.

Roadmap priorizado por componente:

PrioridadeAçãoImpacto no ScoreEsforço
1 Investigar e eliminar anomalias de custo ativas Cost Health ↑ significativo Baixo (horas)
2 Atualizar recursos em Extended Support (RDS, EKS, Lambda runtimes) Cost Health ↑ + elimina custo extra direto Médio (semanas)
3 Comprar Savings Plans para carga base (Compute SP — mais flexível) Cost Health ↑ + Commitment Coverage para Run Baixo (decisão financeira)
4 Eliminar recursos ociosos (EBS, EIPs, snapshots antigos, instâncias paradas) Cost Health ↑ + Waste Elimination para Run Baixo (horas)
5 Redimensionar instâncias superprovisionadas (<10% CPU médio) Cost Health ↑ + Rightsizing para Run Alto (requer aprovações)
6 Implementar política de tags obrigatórias e ativar chaves no Cost Explorer Tagging para Run Médio (1–2 semanas)
7 Ativar Cost Anomaly Detection + AWS Budgets com alertas SNS Governance para Walk/Run Baixo (configuração)

Tendência de Custo

Além do FinOps Score, o dashboard exibe um indicador de tendência de custo — um status qualitativo que compara os 2 últimos meses completos e projeta os próximos 3 meses. A tendência é independente do score e serve como sinal de alarme precoce.

StatusCritérioInterpretaçãoAção Recomendada
Alerta Crescimento mês a mês >15% Custo aumentando rapidamente — pode indicar anomalia, novo workload ou desperdício Investigar serviços crescendo, verificar anomalias
Atenção Crescimento 5–15% Crescimento moderado — monitorar e entender drivers Identificar serviços em crescimento e validar se é justificado
Estável Variação <5% (para cima ou baixo) Custo controlado dentro do esperado Manter práticas atuais
Otimizando Queda >5% Ações de otimização estão gerando resultado mensurável Continuar iniciativas em andamento

O card de tendência também exibe:

  • Variação MoM (%): diferença percentual entre o mês atual e o anterior
  • Média dos últimos 3 meses: baseline para comparação
  • Projeção 3 meses: estimativa do custo futuro com base na tendência atual
  • Serviços com crescimento: lista dos serviços que mais contribuíram para o aumento, com percentual e usage type ofensor
Relação com o FinOps Score: a tendência de custo é um dos sinais que o Claude considera ao calcular o Cost Health Score (componente de 60% do FinOps Score). Um status Alerta penaliza o Cost Health Score mesmo que outros fatores estejam bons.

Quick Wins & Projetos

A IA classifica todas as recomendações em dois grupos: Quick Wins (alta relação impacto/esforço) e Projetos Estratégicos (maior complexidade). Ambos são gerados para FinOps e Segurança separadamente, mas exibidos de forma combinada no portal do cliente.

⚡ Quick Wins

  • Implementáveis em horas ou poucos dias
  • ROI imediato — savings mensais estimados
  • Risco baixo ou médio
  • Categorias: compute, storage, network, database, commitments, version_upgrade, anomaly

🏗️ Projetos Estratégicos

  • Esforço em semanas
  • Impacto estrutural (arquitetura, compliance, governança)
  • Exigem planejamento e aprovação
  • Categorias: architecture, commitments, compliance, monitoring

Ferramentas Avançadas

🔍 Auditoria CloudTrail

Ferramenta de investigação que lista todos os recursos criados na conta por usuários externos. Útil para detectar provisionamento não autorizado ou shadow IT.

Como funciona

  • Consulta o cloudtrail:LookupEvents com filtro ReadOnly=false
  • Filtra apenas eventos de criação (RunInstances, CreateBucket, CreateDBInstance, CreateFunction, etc. — 50+ event names)
  • Descarta eventos onde o ARN ou username contém o identificador do sistema configurado
  • Descarta chamadas que retornaram erro (recurso não criado efetivamente)
  • Range configurável: 1, 3, 7, 14 ou 30 dias
Filtro por ARN: o sistema checa o ARN completo — não apenas o username. Assim, um usuário que acessa via role interna é corretamente identificado como sistema e ignorado.

🛡️ Prowler Integration

Integração com o Prowler — ferramenta open-source de segurança que executa 400+ verificações baseadas em benchmarks CIS, NIST, SOC2 e PCI-DSS.

Fluxo de execução

  • Scan iniciado pelo consultor via botão no painel (POST /admin/clients/{id}/prowler-scan)
  • Execução em background thread — não bloqueia o servidor
  • Saída em formato JSON-OCSF (--output-formats json-ocsf)
  • Duração: 30–60 minutos (timeout máximo: 2h)
  • Página auto-refresh a cada 30s enquanto em andamento
  • Findings agrupados por severidade: Critical → High → Medium → Low → Info
  • Apenas findings com status FAIL são exibidos
Instalação: o Prowler é opcional e instalado separadamente (pip install prowler). Se não instalado, o botão aparece desabilitado com instrução de instalação.
